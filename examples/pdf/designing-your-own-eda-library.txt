=== MODULE 1 — What is a Python library? ===

--- SLIDE 7 --- Script vs Library
Script:  e.g. `python analyze.py` — less work, less convenient, limited scope
Library: e.g. `import simple_eda` — more work, more convenient, broad scope

--- SLIDE 8 --- Scope of our Library
Exploratory Data Analysis helps you understand a dataset: rows, columns, data
types, missing values, basic statistics. Our library will inspect data, not
clean it automatically.

--- SLIDE 9 --- A tiny library can still be real
It does not need a web app; a fancy dashboard; or dozens of dependencies.
It only needs to be useful, installable, and importable.

--- SLIDE 10 --- Library bare minimums
1. Package name  2. Folder  3. __init__.py file  4. Functions  5. Metadata

--- SLIDE 11 --- Package name & folder
You choose — the name needs to be unique.

--- SLIDE 12 --- __init__.py  [header in source reads "Module 3"]

--- SLIDE 13 --- The functions
summarize(df)  missing(df)  numeric_columns(df)  categorical_columns(df)

--- SLIDE 14 --- The beginner rule
Make the first version boring. Use names people can guess. Return familiar
pandas/Python objects. Improve only after the first version works.
Version 0.1.0 is allowed to be tiny.

--- SLIDE 15 --- What counts as success?
A user can pip install it; import it; call one useful function; and read the

--- SLIDE 16 --- Module 1 checkpoint

=== MODULE 2 — Design the smallest EDA API ===

--- SLIDE 17 --- Module 2 opener
The API is what users remember. Build tiny. Install locally. Publish safely.

--- SLIDE 18 --- Start with the user sentence
If the first example feels simple, the library feels simple.
    import simple_eda as eda
    eda.summarize(df)

--- SLIDE 19 --- Pick boring function names
Good names: summarize, missing, numeric_columns, categorical_columns
Avoid clever names: hyper_profile_engine, magic_diagnose, auto_ai_report,
mega_summary

--- SLIDE 20 --- One input type at first
Support pandas DataFrames first. Do not support Polars, Spark, Dask, or Arrow
yet. One clear input type reduces bugs and teaching complexity. Beginner-
friendly means fewer choices.

--- SLIDE 21 --- Return plain objects first
Dictionaries, lists, Series, and DataFrames are enough.
    {"rows": 100, "columns": 5, "column_names": ["city", "sales"]}

--- SLIDE 22 --- Do not mutate user data
Good: df.isna().sum(); df.describe(); list(df.columns)
Bad:  df.dropna(inplace=True); df["x"] = ...; silent type conversion

--- SLIDE 23 --- Keep dependencies small
Use pandas only for version 0.1.0. Every dependency adds install time and risk.
Add visualization libraries only when the core library already works. Small
dependency lists are beginner-friendly and safer.

--- SLIDE 24 --- API surface area
Public: functions users call directly — `eda.summarize(df)`
Internal: helper functions you may change later — `_simple_helper(df)`
Expose only what you want to support.

--- SLIDE 25 --- Good defaults
A function should work without many arguments. Arguments should be optional
when possible. Use sensible behavior before adding configuration.

--- SLIDE 26 --- Naming checklist
Can a beginner guess what it does? Is the name short? Is it a verb or clear
noun phrase? Does it avoid abbreviations? Does it match the README example?

--- SLIDE 27 --- Version 0.1.0 mindset
First working version. Not feature-complete. Not perfect. Installable and
understandable. The goal is momentum, not completeness.

--- SLIDE 28 --- Design decision record
Library name: simple_eda | Install name: simple-eda-yourname | Core dependency:
pandas | Public functions: four EDA helpers.

--- SLIDE 29 --- Module 2 checkpoint
The API is tiny; the names are obvious; the input is pandas only; the library
never changes the user's dataframe. Next: create the package folder.

=== MODULE 4 — Write the first EDA functions ===

--- SLIDE 43 --- Module 4 opener
Start with plain pandas helpers.

--- SLIDE 44 --- Write summarize()
    def summarize(df):
        """Return a small summary of a pandas DataFrame."""
        return {
            "rows": len(df),
            "columns": len(df.columns),
            "column_names": list(df.columns),
            "dtypes": df.dtypes.astype(str).to_dict(),
        }

--- SLIDE 45 --- What summarize() returns
Number of rows; number of columns; column names; data types converted to
strings. This is simple, but immediately useful.

--- SLIDE 46 --- Write missing()
    def missing(df):
        """Return missing-value counts for each column."""
        return df.isna().sum().sort_values(ascending=False)

--- SLIDE 47 --- Why missing values first?
Missing values are one of the first EDA questions; pandas already has the
building blocks; sorting makes the output easier to scan.

--- SLIDE 48 --- Write numeric_columns()
    def numeric_columns(df):
        """Return the names of numeric columns."""
        return list(df.select_dtypes(include="number").columns)

--- SLIDE 49 --- Write categorical_columns()
    def categorical_columns(df):
        """Return object/category column names."""
        return list(df.select_dtypes(include=["object", "category"]).columns)

--- SLIDE 50 --- Optional stats()
This is optional because pandas already does it well.
    def stats(df):
        """Return basic descriptive statistics."""
        return df.describe()

--- SLIDE 51-52 --- Complete core.py
    def summarize(df):
        return {
            "rows": len(df),
            "columns": len(df.columns),
            "column_names": list(df.columns),
            "dtypes": df.dtypes.astype(str).to_dict(),
        }
    def missing(df):
        return df.isna().sum().sort_values(ascending=False)
    def numeric_columns(df):
        return list(df.select_dtypes(include="number").columns)
    def categorical_columns(df):
        return list(df.select_dtypes(include=["object", "category"]).columns)
    def stats(df):
        return df.describe()

--- SLIDE 53 --- Expose functions in __init__.py
    from .core import (
        summarize, missing, numeric_columns, categorical_columns, stats,
    )

--- SLIDE 54 --- Add __all__

--- SLIDE 58 --- Docstrings matter
They show up in help(); they help autocomplete tools; they explain purpose
without a docs site. Short docstrings are enough for version 0.1.0.

--- SLIDE 59 --- No custom classes yet
Custom classes are useful later. Beginners understand dicts, lists, and pandas
Series. Plain objects are easier to test and print. Avoid architecture until you
feel pain.

--- SLIDE 60 --- Common function mistakes
Changing df in place; returning printed text instead of data; adding too many
optional arguments; trying to solve every EDA problem in one function.

--- SLIDE 61 --- Module 4 checkpoint
core.py has useful functions; __init__.py imports them; users can call
eda.summarize(df); functions return simple objects; the dataframe is not
modified.

=== MODULE 8 — Publish safely ===

--- SLIDE 102 --- Module 8 opener
Practice on TestPyPI before uploading to real PyPI.

--- SLIDE 103 --- Why TestPyPI first?
It is a practice package index; you can test upload commands; you can test
install commands; mistakes are less painful than on real PyPI.

--- SLIDE 104 --- Create accounts
Create a TestPyPI account; create a PyPI account; enable two-factor
authentication; create an API token; store the token safely.

--- SLIDE 105 --- Install Twine
    python -m pip install twine

--- SLIDE 106 --- Check the package
Fix errors before uploading.
    python -m twine check dist/*

--- SLIDE 107 --- Upload to TestPyPI
Use your TestPyPI API token when prompted.
    python -m twine upload --repository testpypi dist/*

--- SLIDE 108 --- Install from TestPyPI
    python -m pip install \
      --index-url https://test.pypi.org/simple/ \
      --extra-index-url https://pypi.org/simple/ \
      simple-eda-yourname

--- SLIDE 109 --- Why extra-index-url?
TestPyPI may not have pandas; extra-index-url lets pip find dependencies on real
PyPI; your package still comes from TestPyPI.

--- SLIDE 110 --- Test the TestPyPI install
    python -c "import simple_eda as eda; print(eda.__all__)"

--- SLIDE 111 --- Upload to real PyPI
Only do this after TestPyPI works.
    python -m twine upload dist/*

--- SLIDE 112 --- Install from real PyPI
    pip install simple-eda-yourname
    python -c "import simple_eda"

--- SLIDE 113 --- Publishing safety
Use API tokens, not passwords; do not upload secrets; do not commit tokens;
review dependencies; protect your maintainer account.

--- SLIDE 114 --- pip install can be risky
Packages can execute code during build or runtime; typosquatting can trick
users; compromised maintainer accounts can publish bad updates. Fewer
dependencies means less attack surface. Small packages are easier to trust.

--- SLIDE 115 --- Module 8 checkpoint
twine check passes; TestPyPI upload works; TestPyPI install works; real PyPI

APPENDIX — Logic corrections for beginners
================================================================
The source is solid, but a few points are inconsistent or confusing for a
first-timer. The derived deck (examples/designing-your-own-eda-library.yaml)
applies these fixes:

1. How many functions are there? (3 vs 4 vs 5)
   Slide 3 demos 3 calls; slide 5 says "design 4 functions"; slide 13 lists 4;
   slides 50-54 add `stats()`, making 5 in core.py and __all__.
   FIX: state it consistently everywhere — FOUR core functions (summarize,
   missing, numeric_columns, categorical_columns) PLUS one optional helper
   (stats). The demo and journey slides say "four core functions."

2. __init__.py is introduced three times, once under the wrong module label.
   It appears on slide 10 (as bare-minimum #3), slide 12 (whose header wrongly
   reads "Module 3" while sitting inside the Module 1 run), and slide 36 (its
   real home in Module 3).
   FIX: mention __init__.py once as a bare minimum in Module 1, then explain it
   exactly once — in Module 3, where the folder is actually built. The stray
   mislabeled slide is dropped.

3. "Metadata" (bare-minimum #5) is unexplained where it first appears.
   Slide 10 lists "Metadata" with no context; it is only defined in Module 5.
   FIX: name it "Metadata — the pyproject.toml file" and point forward to
   Module 5 so beginners aren't left guessing.

4. Install-name vs import-name (hyphen vs underscore) is repeated three times
   (slides 32, 41, 69) but never stated as one crisp rule up front.
   FIX: state the rule once, prominently, when the folder is created:
   "hyphens to install (pip/PyPI), underscores to import (Python)."

5. `stats()` is called "optional" but then silently included in the complete
   core.py and in __all__ — a small contradiction.
   FIX: keep it clearly labelled the optional fifth function wherever it appears.

Editorial (necessity) decisions — what was NOT reproduced 1:1:
 - The nine near-identical "Module N checkpoint" slides are folded into a single
   final checklist.
 - The tagline "Build tiny. Install locally. Publish safely.", repeated on every
   module-opener slide, becomes ONE pull-quote (the deck's mantra).
 - Several one-line code slides (e.g. the two column-helper functions; the two
   build commands) are combined onto a single slide each.
